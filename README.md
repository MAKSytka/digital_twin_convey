# Digital Twin Convey

Цифровой двойник трёх ключевых узлов автоматизированной сортировочной линии на базе **ROS 2 Jazzy**, **Gazebo Harmonic / Gazebo Sim 8** и классического машинного зрения OpenCV.

> Репозиторий подготовлен как самостоятельная точка входа для экспертной проверки. Все демонстрации запускаются независимо: матрица сингуляризации, полноширинный инфид-сепаратор и станция операций с КТЯ.

## Быстрая навигация

| Что проверить | Команда | Подробности |
|---|---|---|
| Матрица сингуляризации и роликовое горлышко | `bash ./scripts/run_roller_demo.sh` | [DEMO_SCENARIOS.md](docs/DEMO_SCENARIOS.md) |
| Инфид-сепаратор | `ros2 launch singulator_bringup infeed_size_separator_demo.launch.py` | [INFEED_SIZE_SEPARATOR.md](docs/INFEED_SIZE_SEPARATOR.md) |
| Станция КТЯ, уплотнение и RGB-D | `bash ./scripts/run_kty_perception_3d.sh` | [KTY_RUNTIME_COMMANDS.md](docs/KTY_RUNTIME_COMMANDS.md) |
| Статическая проверка проекта | `python3 tools/validate_project.py` | [TROUBLESHOOTING.md](docs/TROUBLESHOOTING.md) |

## 1. Назначение решения

Целевая инженерная система должна обрабатывать суммарный поток до **100 000 товаров/ч**, работать с 400 логическими направлениями сортировки и принимать товары размером от **15×35×10 мм** до **400×320×280 мм**, массой от **10 г** до **5 кг**.

Репозиторий подтверждает применимость решения цифровыми моделями отдельных узлов:

1. **Инфид-сепаратор** удаляет из основного потока товары, небезопасные для крупноячеистой матрицы.
2. **Матрица сингуляризации** формирует продольные интервалы между товарами и уменьшает ошибку ориентации перед роликовым горлышком.
3. **Станция КТЯ** принимает товары, оценивает заполнение, выполняет виброуплотнение, отводит заполненную тару и подаёт следующую.

Целевые 100 000 товаров/ч достигаются системой из нескольких параллельных линий. Одна матрица не заявляется как универсальная линия на весь поток независимо от ассортимента.

## 2. Поддерживаемая среда

- Ubuntu 24.04 LTS;
- ROS 2 Jazzy;
- Gazebo Harmonic / Gazebo Sim 8;
- Python 3.12;
- `colcon`, `rosdep`;
- `ros_gz_sim`, `ros_gz_bridge`, `ros_gz_image`;
- OpenCV, NumPy, PyYAML, `cv_bridge`;
- 4 ГБ ОЗУ минимум, 8 ГБ рекомендуется;
- дискретный GPU рекомендуется, но вычислительные ROS-узлы могут работать без Gazebo GUI;
- доступ в интернет необходим для первой установки зависимостей.

Ожидаемое время сборки на проверенной машине: **15–20 с**. Типичный RTF сложных сцен: **0,2–0,8**, в зависимости от CPU/GPU, GUI и числа товаров.

### Актуальная конфигурация реализации

| Параметр | Значение |
|---|---:|
| Матрица | 18×4 |
| Независимые зоны | 72 |
| Активная поверхность ячейки | 360×175 мм |
| Продольный/поперечный зазор | 20/20 мм |
| Базовая скорость потока | 2,0–2,5 м/с |
| Диапазон команд ячеек | 1,0–3,0 м/с |
| Ограничение ускорения в текущем контроллере | 6,0 м/с² |
| Продольное трение `mu` | 0,8 |
| Поперечное трение `mu2` | 0,2 — проверенная рабочая калибровка |
| Целевой межтоварный зазор | 0,18 м |
| Межволновой зазор | 0,28 м |
| Частота управления | 30 Гц |
| Фиксированный seed | 42 |

`2g ≈ 19,6 м/с²` не используется как штатное ограничение: это слишком агрессивная стартовая оценка для лёгких и высоких упаковок. В текущем рабочем launch-файле применяется **6 м/с²**. Значение оставлено как воспроизводимая инженерная настройка до стендовой идентификации приводов и проверки опрокидывания.

### Как назначаются скорости ячеек

1. Машинное зрение публикует для каждого товара ID, центр, размеры, yaw и оценку скорости.
2. Контроллер сохраняет глобальный порядок товаров и рассчитывает ошибку зазора каждой соседней пары.
3. Для лидера и следующего товара строятся целевые эффективные скорости: лидер ускоряется, следующий товар замедляется в пределах допустимых границ.
4. Геометрия товара пересекается с сеткой матрицы; каждой затронутой ячейке назначается вес по площади контакта.
5. Если несколько товаров делят одну ячейку, используется bounded coordinate-descent allocator, минимизирующий ошибку между требуемой скоростью товара и фактической overlap-взвешенной скоростью опорных ячеек.
6. Ближе к выходу deadline-recovery увеличивает минимальную разность скоростей, если требуемый зазор ещё не сформирован.
7. Поперечная разность скоростей под товаром создаёт момент для коррекции yaw; в плотных кластерах вращение подавляется, чтобы не ухудшать продольное разделение.
8. Итоговый массив из 72 скоростей публикуется fan-out узлом в индивидуальные команды приводов.

Подробно: [SINGULATION_CONTROL.md](docs/SINGULATION_CONTROL.md).

### Машинное зрение матрицы

Поток кадров поступает из камеры Gazebo. Нейросеть не используется. Классический CV-контур формирует наблюдения товаров и отображает обработку в реальном времени.

```bash

```

Нагрузочный конечный сценарий:

```bash
ros2 launch singulator_bringup \

  spawn_mode:=finite \
  maximum_items:=200 \
  target_rate_boxes_per_sec:=4.0 \
  small_item_probability:=0.50 \

```

Основные параметры:

- рабочая ширина 2,5 м;
- скорость 2,0 м/с;
- 11 валов по 25 дисков;
- радиус контакта 25 мм;
- 80 рад/с, около 763,9 об/мин;
- открытые промежутки 70×70 мм;
- переходы: 1 мм по горизонтали и ступень 4 мм вниз;
- классификация по минимальной опорной проекции;
- автоматический контроль маршрута и despawn.

## 6. Демонстрация станции КТЯ

```bash
cd ~/singulator_digital_twin
source /opt/ros/jazzy/setup.bash
bash ./scripts/build_kty_perception_3d.sh
source install/setup.bash
bash ./scripts/run_kty_perception_3d.sh
```

Проверка во втором терминале:

```bash
source /opt/ros/jazzy/setup.bash
source install/setup.bash
bash ./scripts/check_kty_runtime_v18.sh
```

Успешный тест: минимум четыре разных цикла `LOAD` без `ERROR`.

Рабочий цикл:

```text
LOAD
→ CLOSE_GATE
→ COMPACT
→ EJECT_ACTIVE
→ DESPAWN_ACTIVE
→ POSITION_NEXT
→ VERIFY_READY
→ OPEN_GATE
→ LOAD
```

## 7. Нагрузочные сценарии

Сценарии должны запускаться с фиксированным `seed:=42`:

1. **Номинальный:** параметры по умолчанию, стабильная работа и воспроизводимый поток.
2. **Повышенная нагрузка:** интенсивность увеличивается ступенями; фиксируются RTF, число активных товаров, ошибки зазора и длина очереди.
3. **Перегрузка:** входная интенсивность выше устойчивой пропускной способности; система должна ограничивать команды, сохранять порядок, логировать дефицит производительности и не скрывать затор искусственным удалением товара.
4. **Восстановление:** после перегрузки интенсивность возвращается к номинальной; очередь должна уменьшаться без перезапуска.

Команды и критерии: [DEMO_SCENARIOS.md](docs/DEMO_SCENARIOS.md).

Полный runtime необходимо проверять на Ubuntu 24.04 с ROS 2 Jazzy и Gazebo Harmonic. CI выполняет статическую проверку Python, XML/SDF, shell-скриптов и cross-file wiring, но не заменяет физический прогон Gazebo.

## 11. Известные ограничения

- проект проверен на одном основном ПК, а не на чистом парке машин;
- RTF зависит от оборудования и числа активных динамических моделей;
- параметры трения и ускорения являются калибровочными параметрами цифровой модели;
- одна верхняя RGB-D камера не может гарантированно разделить одинаковые по цвету и высоте коробки без видимого шва;
- интеграция с внешней WMS имитируется: формирование маршрута не входит в задачу данного репозитория;
- Docker-образ пока не поддерживается.
