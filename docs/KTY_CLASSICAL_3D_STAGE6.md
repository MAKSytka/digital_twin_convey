# KTY stage 6: классическое 3D-распознавание коробок

Этап заменяет прежнее разделение по одной бинарной маске комбинированным
классическим RGB-D алгоритмом. Цель — устойчивее разделять соприкасающиеся
коробки и подготовить геометрию для будущего робота-манипулятора без обучения
нейросети.

## Обработка кадра

```text
RGB + depth
  -> восстановление пропусков глубины
  -> bilateral filtering
  -> карта высоты над дном КТЯ
  -> границы по скачку depth
  -> границы по изменению высоты
  -> границы по изменению нормали
  -> слабое усиление RGB-границ
  -> локальные 3D-максимумы
  -> marker-controlled watershed
  -> отдельные instances
  -> OBB + нормаль + размеры
  -> temporal tracking
  -> grasp candidates
```

Старый алгоритм использовал distance-transform внутри связной компоненты. При
соприкосновении коробок близкой высоты две верхние поверхности могли иметь одну
широкую область и объединяться. Новый алгоритм строит маркеры одновременно по
геометрическому расстоянию, локальной высоте и силе 3D-границы.

## Границы объекта

Итоговая карта границ объединяет:

```text
42% — градиент depth
28% — градиент высоты
22% — изменение нормалей поверхности
 8% — RGB-граница
```

RGB имеет небольшой вес: алгоритм должен продолжать работать для соседних
коробок одинакового цвета. Цвет помогает только в неоднозначных местах.

## Маркеры watershed

Кандидаты маркеров выбираются в глубине компоненты и около локальных максимумов
карты высоты. Затем применяется подавление близких максимумов. Стартовые
параметры:

```text
минимальное расстояние маркеров: 18 px
минимальная выраженность высоты: 12 мм
порог depth-границы:             10 мм
порог изменения нормали:         0,12
```

Эти значения являются начальными и должны быть откалиброваны по сохранённым
кадрам симуляции.

## Выход объекта

`KtyProductContour` расширен следующими полями:

```text
tracking_state
oriented_rectangle
surface_normal
estimated_size
 yaw_rad
occlusion_score
top_accessible
grasp_candidates[]
```

Существующие поля `polygon`, `centroid`, `top_height_m`, `confidence` и
доступность четырёх сторон сохранены.

## Состояния трека

```text
VISIBLE
OCCLUDED
```

Когда объект временно закрыт другой коробкой или пропал из сегментации, его ID
сохраняется в состоянии `OCCLUDED` в течение ограниченного числа кадров.

Обязательное правило:

```text
OCCLUDED -> grasp_candidates = []
```

То есть робот получает историю скрытого объекта, но не получает разрешение на
его захват.

## Oriented bounding box

Для видимой проекции строится минимальный ориентированный прямоугольник. Из него
получаются:

- длина и ширина;
- угол `yaw`;
- четыре точки OBB;
- приближённый размер `XYZ`;
- положение центра верхней поверхности.

Высота пока оценивается относительно дна КТЯ. Полный 3D OBB нижней скрытой части
коробки является приближением, а не прямым измерением.

## Нормаль поверхности

Нормаль вычисляется по производным карты высоты. Верхний захват разрешается,
когда одновременно:

```text
normal.z >= 0,82
occlusion_score <= 0,42
confidence >= 0,58
tracking_state == VISIBLE
```

## Кандидаты захвата

Для доступной верхней поверхности публикуется:

```text
TOP_CENTER
```

При достаточном боковом зазоре дополнительно создаются:

```text
SIDE_NEG_X
SIDE_POS_X
SIDE_NEG_Y
SIDE_POS_Y
```

Каждый кандидат содержит:

- позу;
- вектор подхода;
- оценку качества;
- требуемый зазор;
- название стратегии.

Это ещё не готовая траектория MoveIt: отсутствуют hand-eye калибровка,
кинематические ограничения робота и проверка коллизий руки.

## Сохранение

Расширенный recorder публикует и сохраняет схему:

```text
kty_carton_instances_3d/v2
```

Файлы:

```text
~/.ros/kty_vision/polygons_latest.json
~/.ros/kty_vision/polygons.jsonl
```

В JSON сохраняются видимый полигон, OBB, нормаль, размеры, состояние трека,
коэффициент перекрытия и все допустимые кандидаты захвата.

## Dashboard

Расширенный dashboard показывает:

- исходный контур зелёным;
- OBB отдельной линией;
- точки и направления кандидатов захвата;
- число `VISIBLE` и `OCCLUDED` треков;
- число доступных верхних объектов;
- общее число grasp candidates.

## Сборка

```bash
cd ~/singulator_digital_twin
chmod +x scripts/*kty_perception_3d.sh tools/validate_kty_classical_3d.py
python3 tools/validate_kty_classical_3d.py
bash ./scripts/build_kty_perception_3d.sh
```

## Запуск

```bash
source /opt/ros/jazzy/setup.bash
source install/setup.bash
bash ./scripts/run_kty_perception_3d.sh
```

## Диагностика

```bash
bash ./scripts/check_kty_perception_3d.sh
```

Скрипт требует:

1. хотя бы один видимый объект;
2. полигон минимум из трёх точек;
3. OBB ровно из четырёх точек;
4. положительные оценённые размеры;
5. валидную нормаль;
6. хотя бы один кандидат захвата;
7. отсутствие кандидатов у `OCCLUDED`;
8. JSON-схему `kty_carton_instances_3d/v2`.

## Ручная проверка

```bash
ros2 topic echo /kty/perception/contours --once
python3 -m json.tool ~/.ros/kty_vision/polygons_latest.json
```

## Ограничения

- две плотно соприкасающиеся коробки одинаковой высоты, цвета и без видимого
  шва физически неразличимы для одной верхней RGB-D камеры;
- сложные стопки могут потребовать второй камеры или learned instance
  segmentation;
- текущий tracker использует геометрическое сопоставление, а не Kalman filter;
- параметры следует настраивать по записанному набору сложных сцен;
- grasp candidates находятся в системе `kty_inner`, а не в базе робота.
