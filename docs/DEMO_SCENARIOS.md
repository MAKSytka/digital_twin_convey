# Сценарии проверки экспертной комиссией

Все измеримые сценарии запускаются с фиксированным `seed=42`. Перед демонстрацией необходимо записать commit SHA, версии ROS/Gazebo и вывод валидаторов.

## 0. Preflight

```bash
cd ~/singulator_digital_twin
source /opt/ros/jazzy/setup.bash
source install/setup.bash

python3 tools/validate_project.py
python3 tools/validate_separator_demo.py
python3 tools/validate_kty_runtime_v18.py
python3 tools/test_v7_logic.py
```

## 1. Матрица: номинальный режим

```bash
bash ./scripts/run_roller_demo.sh
```

Во втором терминале:

```bash
source /opt/ros/jazzy/setup.bash
source install/setup.bash
bash ./scripts/check_vision.sh
bash ./scripts/check_v7_control.sh
```

### Что показать

- хаотический многорядный поток;
- реальные bounding boxes/ID машинного зрения;
- изменение индивидуальных скоростей ячеек;
- рост зазора между соседними товарами;
- коррекцию yaw;
- прохождение роликового горлышка;
- массив из 72 команд без выхода за 1–3 м/с.

### Критерии

- контроллер не теряет глобальный порядок;
- нет обратного движения товара;
- наблюдения обновляются в реальном времени;
- выходной зазор стремится к 0,18 м;
- отсутствуют необъяснимые despawn внутри активной зоны.

## 2. Матрица: ступенчатый рост нагрузки

Запустить штатную демонстрацию, затем увеличивать параметр входной интенсивности ступенями. Конкретное имя launch-параметра нужно смотреть через:

```bash
ros2 launch singulator_bringup matrix_stream_roller.launch.py --show-args
```

Рекомендуемая программа:

```text
этап A: 4 товара/с, 60 с
этап B: 6 товаров/с, 60 с
этап C: 8 товаров/с, 60 с
этап D: возврат к 4 товарам/с, 90 с
```

Если текущий launcher не предоставляет параметр интенсивности, изменять его следует через штатный параметр spawner, а не редактированием SDF во время защиты.

### Фиксировать

- RTF;
- активное число товаров;
- среднюю и максимальную ошибку зазора;
- число deadline boosts;
- число uncontrollable/shared-cell конфликтов;
- время освобождения очереди после возврата к номиналу.

### Ожидаемая реакция

При росте нагрузки контроллер должен насыщать команды в допустимом диапазоне и честно показывать недостаток управляющего ресурса. Допустима очередь; недопустимы NaN, неограниченные скорости, перестановка ID и скрытое удаление товаров.

## 3. Инфид-сепаратор: конечный прогон

```bash
ros2 launch singulator_bringup \
  infeed_size_separator_demo.launch.py \
  spawn_mode:=finite \
  maximum_items:=200 \
  target_rate_boxes_per_sec:=4.0 \
  small_item_probability:=0.50 \
  seed:=42
```

### Что показать

- 11 физических валов;
- прохождение крупных товаров по верхней ветви;
- падение малых/узких товаров на нижнюю ветвь;
- работу переходов без устойчивого затора;
- рост счётчиков `upper`, `lower`, `removed`;
- `remove_failures=0` и `monitor_restarts=0` в штатном прогоне.

## 4. Станция КТЯ: четыре непрерывных цикла

```bash
bash ./scripts/run_kty_perception_3d.sh
```

Во втором терминале:

```bash
bash ./scripts/check_kty_runtime_v18.sh
```

В третьем терминале открыть dashboard:

```bash
ros2 run kty_station_sim vision_dashboard_3d \
  --ros-args \
  -r __node:=kty_vision_dashboard_window \
  -p show_window:=true \
  -p refresh_hz:=3.0
```

### Что показать

- активный и ожидающий КТЯ;
- загрузку и оценку заполнения;
- закрытие створки;
- физическое виброуплотнение;
- RGB-D контуры, OBB, ID и grasp candidates;
- отвод и удаление заполненного КТЯ;
- подачу следующего КТЯ без ручного вмешательства.

### Критерии

- четыре состояния `LOAD` для разных циклов;
- нет `ERROR`;
- `position_recovery_failures=0`;
- dashboard не блокирует основной runtime;
- файлы JSON/JSONL обновляются.

## 5. Headless-проверка

GUI Gazebo не является обязательным для вычислительных узлов. Для проверки на ограниченном сервере запустить launch с отключённым GUI, если соответствующий аргумент доступен, а dashboard публиковать как ROS Image topic.

```bash
ros2 topic hz /kty/vision/dashboard
ros2 topic hz /kty/perception/contours
```

## 6. Что считать неуспехом

- мир запущен, но ROS-контроллер отсутствует;
- `/clock` не растёт при `use_sim_time=true`;
- размер массива команд не совпадает с 72;
- товар проходит через видимую коллизию;
- RTF падает, а система скрывает проблему принудительным перемещением товара;
- dashboard использует ground truth вместо RGB-D для распознавания;
- после заполнения КТЯ цикл не переходит к следующей таре.
