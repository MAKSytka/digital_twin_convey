# Handoff: стабильный runtime станции КТЯ v18

## Назначение

Документ фиксирует конфигурацию станции операций с КТЯ, команды проверки и критерии приёмки перед финальным merge.

Рабочая release-ветка:

```text
chore/final-project-packaging
```

После merge те же команды должны выполняться из `main`. Переключение на исторические KTY-ветки не требуется.

## Рабочий цикл

```text
LOAD
→ CLOSE_GATE
→ COMPACT
→ EJECT_ACTIVE
→ DESPAWN_ACTIVE
→ POSITION_NEXT
→ VERIFY_READY
→ OPEN_GATE
→ LOAD следующего КТЯ
```

Система включает:

- два КТЯ одновременно: активный и ожидающий;
- параллельный отвод заполненного и предварительную подачу следующего;
- плоские контактные транспортные зоны без роликов;
- статическую задвижку лотка с подтверждением через JSON-реестр Gazebo;
- статический позиционирующий упор;
- удаление заполненного КТЯ и находившихся в нём товаров;
- восстановление пустого ожидающего КТЯ при редком заклинивании;
- RGB-D оценку заполнения;
- классическую 3D-сегментацию товаров;
- OBB, полигоны, нормали и кандидаты захвата;
- виброуплотнение;
- dashboard машинного зрения.

## Направляющие лотка

Исходный наклонный лоток имеет рабочую поверхность шириной 600 мм и параллельные наружные борта. В финальном runtime поверх них добавлена вторая пара высоких сходящихся направляющих:

| Параметр | Значение |
|---|---:|
| Число дополнительных направляющих | 2 |
| Длина | 1,010 м |
| Толщина | 0,030 м |
| Высота | 0,240 м |
| Угол схождения | около ±4,57° |
| Внутренняя ширина у входа | около 565 мм |
| Внутренняя ширина у выхода | около 400 мм |
| Коэффициент восстановления | 0,0 |

Направляющие сходятся к внутренней ширине КТЯ 400 мм. Они не управляют маршрутом программно: товар перенаправляется в КТЯ физическими контактами с боковыми стенками.

Геометрия создаётся генератором:

```text
src/kty_station_sim/kty_station_sim/world_patch_v4.py
```

## Ограничение поперечного спавна

Спавн товаров на лотке теперь учитывает не только координату центра, но и yaw-зависимую поперечную проекцию упаковки:

```text
half_projection_y = 0.5 ×
  (|size_x × sin(yaw)| + |size_y × cos(yaw)|)
```

Приняты ограничения:

```text
product_spawn_center_half_width_m = 0.090
product_landing_half_width_m      = 0.170
KTY inner half-width              = 0.200
```

Это означает:

- центр товара создаётся не дальше 90 мм от оси лотка;
- полная поперечная проекция товара должна оставаться внутри ±170 мм;
- до внутренних стенок КТЯ остаётся не менее 30 мм номинального запаса с каждой стороны.

Ограничение вычисляется отдельно для каждого профиля с учётом его размеров и угла, поэтому крупные повёрнутые коробки автоматически спавнятся ближе к центральной линии.

## Зафиксированные runtime-параметры

| Параметр | Значение |
|---|---:|
| Скорость транспортных зон | 0,80 м/с |
| Скорость точного позиционирования | 0,22 м/с |
| Слабая вибрация | 5 Гц, ±1,8 мм |
| Сильная вибрация | свип 6,5–9 Гц, ±8 мм |
| Длительность сильной вибрации | 15 с |
| Интервал спавна при открытой задвижке | 1,90 с |
| Интервал спавна при закрытой задвижке | 3,0 с |
| Максимум товаров при закрытой задвижке | 5 |
| Размеры товаров | 35×15×10 … 280×190×145 мм |
| Порог заполнения | 82% |
| Порог максимальной высоты | 340 мм |
| Высота камеры над дном КТЯ | 1,10 м |
| Внутренний размер КТЯ | 600×400×400 мм |

Настройка заполнения:

```text
fill_ratio_threshold      = 0.82
max_height_threshold_m    = 0.340
camera_to_bottom_m        = 1.10
```

Та же геометрия `1,10 м` используется узлом 3D-perception.

## Архитектура обратной связи

Gazebo-плагин `kty_conveyor_surface` публикует компактный реестр моделей:

```text
/kty/mech/model_pose_registry_json
```

Контроллер использует этот поток для:

- координат КТЯ;
- подтверждения создания и удаления моделей;
- подтверждения состояния задвижки;
- подтверждения состояния позиционирующего упора;
- контроля количества товаров.

Не возвращать частые вызовы `gz topic -e` в рабочий цикл: они ранее приводили к падению `gz-transport-topic` внутри `zmq_poll()`.

## Критерии приёмки

1. наблюдаются четыре разных цикла `LOAD`;
2. отсутствует состояние `ERROR`;
3. заполненный КТЯ удаляется до окончательного позиционирования следующего;
4. задвижка открывается в каждом новом цикле;
5. товары снова начинают поступать после смены КТЯ;
6. `position_recovery_failures = 0`;
7. допускается `position_recovery_respawns > 0`, если цикл продолжается;
8. обе дополнительные направляющие видимы и имеют физические коллизии;
9. товар не покидает лоток через боковые стороны;
10. все профили попадают внутрь КТЯ, а не рядом с ним;
11. направляющие не создают устойчивый затор у выхода лотка;
12. КТЯ заполняется до порогов без переполнения лотка.

Ожидаемый результат диагностического скрипта:

```text
KTY runtime-v18 four-cycle continuity: OK
```

## Статическая проверка

```bash
python3 tools/validate_kty_runtime_v18.py
bash scripts/run_release_checks.sh
```

Валидатор генерирует временный runtime-мир и проверяет наличие обеих направляющих, их размеры, позы, визуалы, коллизии и неупругий контакт.

## Известные особенности

- предупреждения Qt `Binding loop detected` не влияют на физику;
- сообщения Gazebo `Entity ... not found, so not removed` допустимы при идемпотентной очистке;
- RTF зависит от открытого dashboard и производительности GPU/CPU;
- автоматическое восстановление пустого КТЯ является частью отказоустойчивости v18;
- новые направляющие и суженный spawn-envelope требуют повторного четырёхциклового runtime-прогона перед окончательной отметкой `принято`.
